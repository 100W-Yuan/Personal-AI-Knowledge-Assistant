## 2. 五类业务实体及其关系（详见 P1-001-03）

| 实体 | 唯一真相源负责的事实 | 派生（不可单独判定） |
|---|---|---|
| Order | 订单是否关闭 | 对外呈现状态（由三方推导） |
| Payment | 是否支付成功 / 支付时间 | `Order.paid`、`Order.paid_at` |
| Shipment（+TraceEvent） | 揽收、位置、签收 | `Shipment.status` |
| AfterSale | 退款、退货、售后类型 | `Order.status == refunded` |
| WorkOrder | 处理过程与结论引用 | 看板快照 |

关系：Order 1:0..1 Payment｜1:0..1 Shipment（V1 单包裹）｜1:0..N AfterSale（活跃至多 1）｜1:0..N WorkOrder｜WorkOrder 1:N Task。

**核心推论**：`Order.status` 是派生值 → **EX-04 的实质是"派生层与真相源层的偏离检测"**。这解释了 D-06 为何把它排最高：派生逻辑错了，连 EX-01 的排除条件都会失效。

**WorkOrder ≠ Task**：前者是"客服在处理哪件事"，后者是"系统跑了哪段流程"，后者不对外暴露。

## 6. 审批业务规则

| 层级 | 触发 | 谁审 |
|---|---|---|
| L0 | 分析、检索、建议、**草稿生成** | 无 |
| L1 | 草稿"认定可对外"、标准方案（催单/查件/补发申请） | 组长 |
| L2 | 高风险（退款/赔付/改址/取消）、三方状态矛盾、修改后动作升级 | 主管 |

**草稿三态（务必区分）**：`draft`（L0 生成）→ `cleared_for_outbound`（L1 认定可对外，**仍不发送**）→ `sent`（**V1 禁止**）。

**5 种结局**：批准（只写记录）/ 驳回（`failed`）/ 要求修改（`waiting_revision`，限 1 次，原稿 `superseded`，新稿重审不继承）/ 超时（`approval_expired`，**不自动推进**）/ **审批端不可用（fail-closed：宁可卡住，不得放行）**。

> **fail-closed 是本轮最重要的一条业务约定**：知识库不可用可降级，审批不可用**不能**降级为免审批。

## 7. 多 Agent 完整业务流程（12 步）

| # | 步骤 | 角色 | 失败处理 | 重试 | 人工 |
|---|---|---|---|---|---|
| 1 | 客服输入订单号 + 描述 | 客服 | 格式错 → 改输入 | 是 | 否 |
| 2 | 验证输入 | 系统 | 订单不存在 → 明确告知 | 是 | 例外 |
| 3 | 识别与分解 | **Coordinator** | 计划非法 → 重规划（限次） | 是 | 否 |
| 4 | 取数（订单/支付/物流/售后） | **Data Agent** | 缺失/陈旧/同步中 → 标完整性 | 1 次 | 严重缺失转人工 |
| 5 | 检索 SOP 与案例 | **Knowledge Agent** | `no_hit` / `unavailable` | 1 次 | 否 |
| 6 | 判异常 | **Analysis Agent** | 无法归类 → `unclassified` | **否** | 是 |
| 7 | 归并主次 | **Coordinator** | 冲突 → 以 Analysis 为准 + 审计 | 否 | 否 |
| 8 | 生成方案与草稿 | **Service Agent** | 失败 → 不出空稿 | 1 次 | 否 |
| 9 | 判审批层级 | **Coordinator** | 多动作取最高；歧义则升级 | 否 | 歧义时 |
| 10 | 形成最终建议 | Coordinator | 超时/不可用 → 等待 | 等待 | 是 |
| 11 | 写审计 | 系统 | 写入失败 → **不得静默继续** | 是 | 是 |
| 12 | 展示结果 | 系统 → 客服 | 渲染失败 → 重试 | 是 | 否 |

**四步同属 Coordinator 但职责不同**（3 规划 / 7 归并 / 9 分级 / 10 汇总）——这是"多 Agent 分工"而非"单 Agent 工具标签"的体现：每个角色的**权力边界**不同，不是调用的函数不同。
