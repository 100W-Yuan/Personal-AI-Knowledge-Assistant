## 1. 执行摘要

本轮把 P0 的"设计级结论"往下压了一层，落到**可被一线客服理解、可被开发翻译成判断语句**的程度。三件实质推进：

1. **补上了被漏掉的第四个数据源**：P0 的三方矛盾只算订单/物流/售后，但 EX-01 的起算点依赖支付。本轮明确 **Payment 是支付事实的唯一来源，`Order.paid` 是派生值**，并据此提出"EX-01 应从 `Payment.paid_at` 起算"。
2. **把 EX-02 从"48h 没有推进"变成可审查的 15 类事件分类表**，并给出三层状态（代码可解析 / 业务允许 / 负责人批准）——**当前批准数 0，故 EX-02 仍不可实现**。
3. **发现并定义了一条通用判定纪律**：否定性判定（"未揽收""未更新"）必须建立在数据完整性可信之上，否则"没看到"会被误当"没发生"。这条规则同时约束 EX-01 与 EX-03。

**结论（V1.0 原文，保留）**：P1-001 的业务分析已完成，但 **P1 不等于通过**。阻塞点仍是 P0-009 的 C-1（T2 白名单），外加本轮新增的 3 个待确认点。

> **V1.3 对上面第 2 点的更新**：原文"**批准数 0，故 EX-02 仍不可实现**"已部分过时——

## 2. 五类业务实体（详见 P1-001-03）

| 实体 | 唯一真相源负责的业务事实 | 派生（不可单独作判定依据） |
|---|---|---|
| **Order** | 订单是否关闭 | 订单"对外呈现状态"（由三方推导） |
| **Payment** | 是否支付成功、支付成功时间 | `Order.paid`、`Order.paid_at` |
| **Shipment**（+TraceEvent） | 是否揽收、当前位置、是否签收 | `Shipment.status`、`Order.shipping_status` |
| **AfterSale** | 是否退款、退货进度、售后类型 | `Order.status == refunded` |
| **WorkOrder** | 处理过程与结论引用 | 任何看板快照 |

### 2.1 一条结构性推论

`Order.status` 是**派生值**。因此：

> **EX-04 的实质 = "派生层与真相源层的偏离检测"。**

这解释了 D-06 为何把 EX-04 排最高：它不是"某环节异常"，而是"**派生逻辑本身错了**"，连 EX-01 的排除条件（"已退款则排除"）都可能失效。

### 2.2 WorkOrder 与 Task 的区别

| | WorkOrder | Task |
|---|---|---|
| 是什么 | 业务实体：客服在处理哪件事 | 系统执行单元：跑了哪段流程 |
| 谁看 | 一线客服 | 仅系统内部 |
| 基数 | 1 订单 : N 工单（V1 建议活跃至多 1） | 1 工单 : N 任务 |
| 能否产生异常事实 | **不能** | **不能**（只能由 Analysis 签发） |

## 3. EX-01 已支付未揽收（T1 = 72h，不得改动）

### 3.1 支付成功的必要条件

| # | 条件 | 依据 | 状态 |
|---|---|---|---|
| 1 | 存在生效 Payment 记录 | Payment 是唯一真相源 | **D-09 确认**（缺失 → 不判，归待核实） |
| 2 | 该记录状态为"成功" | 同上 | **D-09 确认**（非成功 → 不判） |
| 3 | `paid_at` 非空且不晚于 `as_of` | 起算点要求 | **D-09 确认**（为空 → 不判） |
| 4 | 金额 > 0 | 防"0 元占位单"被当已支付 | **待确认**（D-09 未涉及金额） |
| 5 | 同一订单存在多条支付尝试时，取**成功的那条**为生效支付 | 避免多次支付干扰 | 建议（**D-09 未覆盖**，不得推定） |

> **注意条件 3 与条件 4 的区别**：条件 1~3 已被 D-09 覆盖（"缺失/非成功/空值 → 不判，归待核实"），条件 4（金额 > 0）与条件 5（多条支付取成功那条）**不在 D-09 范围内**，仍为建议/待确认，**不得**因 D-09 已批准而一并当作已确认。

### 3.2 "支付成功时间"的业务含义 —— **已由 D-09 定案**

- **是**：资金到账确认（银行/支付渠道返回成功）的时间；
- **不是**：下单时间、支付发起时间、订单状态变为"已支付"的时间（后者是同步结果）。

> **规则（D-09，已批准）**：T1 起算**唯一取 `Payment.paid_at`**，不取 `Order.paid_at`。
> **理由**：`Order.paid_at` 是同步副本，可能晚于真实支付时间；用它会把"已支付时长"算短 → **漏报**异常。
> **原状态**：V1.0 时为"建议 + 待确认"，原文写作"**清单第 13 项**"——该编号有误，在《P1-001-05 待确认清单》中实为**第 12 项**（两文编号互换，对照表见 P1-001-05 §0）。现由 D-09 关闭。

**D-09 的六条约束与 EX-01 判定式的对应关系**：

| # | D-09 约束 | 落在判定式的哪一步 |
|---|---|---|
| 1 | `Payment.paid_at` 为唯一真相源 | `elapsed = as_of − Payment.paid_at`（唯一算式） |
| 2 | `Order.paid_at` 不得作起算点/不得参与计算/不得回填 | 判定式中**禁止出现** `Order.paid_at` |
| 3 | 不一致时以源为准，并把不一致记为偏离证据 | 证据项新增一条"支付时间偏离"（见 §3.6） |
| 4 | `Payment` 缺失 / 非成功 / `paid_at` 为空 → 不判 EX-01，归 `pending_verification` | 判定入口的第一道分流 |
| 5 | 偏离**只作证据**，不得据此判 EX-04 | 禁止把时间差当矛盾 |
| 6 | T1=72h 不变 | 阈值不动 |

**两处易错点（实现时最容易违反）**：

1. **"不判"必须有去处**：`Payment` 缺失时不是"跳过这个订单"，而是**进待核实队列**。少了这一步，缺失订单会被静默丢弃。
2. **"记证据"不等于"判异常"**：两个 `paid_at` 不相等可能只是同步延迟（D-08），归 `data_stale` 或 `pending_verification`，**不得**判 EX-04。

> **未关闭**：支付一致性**是否作为 EX-04 的附加检查项**仍未定（清单第 15 项）。D-09 只排除了"新增第 5 类异常"这一选项，A/B 之间尚未选择。详见 §6.6。

### 3.3 "物流未揽收"的判定依据

| 情形 | 判定 | 说明 |
|---|---|---|
| 无 Shipment 实体 | **未揽收成立** | 从未建单，"未发货"是确定事实 |
| 有 Shipment，轨迹为空，**有同步正常证据** | **未揽收成立** | 可确认"没有揽收事件" |
| 有 Shipment，轨迹为空，**无同步证据** | **不判**（`data_missing`） | "看不到"≠"没发生" |
| 有轨迹，但无 `picked_up` 及之后事件 | **未揽收成立** | 有轨迹说明同步正常 |
| 有 `picked_up` 或更后事件 | **不成立** | 已揽收 |

**判定纪律**：EX-01 需要**否定性证据**，不是"缺乏肯定性证据"。

### 3.4 排除条件

| 排除情形 | 判定依据（源实体） | 说明 |
|---|---|---|
| 订单已关闭 | `Order.status == closed` | 订单域自身事实 |
| 售后进行中（申请/审核/同意/退货中） | `AfterSale.status ∈ {applied, reviewing, approved, returning}` | 已在处理，不重复报警 |
| 已退款 | `AfterSale.status == refunded` | 资金已退 |
| 风控/合规冻结 | **V1 无此数据源** | 待确认是否需要 |

> **注意**：排除条件本身也依赖源实体。若 AfterSale 缺失而 `Order.status == refunded`（派生值声称已退款），**不得**直接排除——应记"派生与源不一致"，可能是 EX-04 的线索（R-D3）。

### 3.5 时间边界

| 边界 | 处理 | 状态 |
|---|---|---|
| `elapsed == 72h` | **判命中**（`>=` 口径） | 建议，待确认（清单第 3 项） |
| 周末/节假日 | 待确认（清单第 2 项） | 建议 V1 不排除 |
| 跨自然日 | 按绝对时长算，不按"自然日数" | 建议（SC-066） |
| `as_of` 回溯 | 以 `as_of` 为"现在"计算 | 建议 |

### 3.6 证据（evidence）构成

| 证据项 | 内容 |
|---|---|
| `payment_id` + `paid_at` | 起算点凭证（D-09：必须是 `Payment.paid_at`） |
| **支付时间偏离记录** | 若 `Order.paid_at != Payment.paid_at`，记录两者原值与差值（**D-09-3 强制项**）。该记录只作证据，不判异常 |
| `elapsed` | 已支付时长（含单位与 `as_of`） |
| 轨迹完整性声明 | "无物流单" / "有单无轨迹但同步正常" / "轨迹中无揽收事件" |
| 排除项检查结果 | 逐条列出已检查的排除条件及结论 |

> **D-09-3 的执行口径**：偏离记录**无条件**写入，不因"差值很小"而省略。省略等于丢失判断依据——将来若发现某类偏离其实有业务含义，已跑过的单子无法回溯。

## 5. EX-03 长时间未更新（T3 = 72h）

### 5.1 最后一次有效物流轨迹

> **定义（建议）**：`max(时间)` over **事实类**轨迹事件，排除预测类、作废类、重复条目、同步快照。

| 事件类型 | 是否刷新"更新时间" |
|---|---|
| 揽收、到站、离站、运输中、派送中、签收 | ✅ 刷新 |
| 物流异常（破损/丢失） | ✅ 刷新（是真实动作） |
| 预测到达、预计送达 | ❌ 不刷新（非事实） |
| 作废 / 撤销 | ❌ 不刷新 |
| 重复推送 | 去重后按 1 次计 |
| **状态同步快照** | ❌ **不刷新（关键）** |

> **V1.2 补充（P1-003 发现）**：上表按"事件类型"排列，但真正决定是否刷新的**不是类型，而是"事件 vs 状态"**。
>
> 若某类型（如 `in_transit`）在数据源里是**状态**而非事件，它每次同步都会生成新记录，把"更新时间"不断往后推 → **EX-03 永不触发**。这与"状态同步快照"是同一个陷阱，只是换了名字。
>
> 因此上表须补一条**前置判据**：只有带 `event_time` 且不可周期性再生的**离散事件**才可刷新；判据与完整**八类**分类见 **P1-003-01 §1.3/§1.4**（该表 V1.1 起为八类）。
>
> 另：**物流异常（E-08）刷新更新时间但"不构成推进"**——七类分类法无法覆盖这一类，已在 P1-003-01 §2.2 登记为分类法缺口。〔**V1.3：缺口已由 D-12 / R-02 关闭**，`exception` 独立为 C8，见下表〕
>
> **V1.3 更新（P1-004 / D-12）**：
>
> | 上文的表述 | V1.3 状态 |
> |---|---|
> | "须补一条前置判据" | ✅ **判据已批准**（R-01）：只有带 `event_time`、不可周期性再生的离散事件才可刷新；无法确认语义 → `pending_verification`，**不得猜测** |

>

### 6.1 三方状态候选分类

| 方 | 候选状态数 | 说明 |
|---|---|---|

### 6.2 合法组合（8 条，L-1~L-8）

支付前 / 已付待发 / 运输中 / 签收后 / 退货闭环 / 未发货关闭 / **仅退款例外** / 物流异常本身合法。

### 6.3 非法组合（6 类，C-01~C-06）

未发货却签收 / 订单签收物流未签收 / 已关闭仍派送 / 退货退款未退回 / 已退款订单未反映 / 三方全矛盾。

### 6.4 五态区分（D-08 落地）

| 情形 | 归类 | 可判 EX-04 |
|---|---|---|
| 数据缺失 | `data_missing` | ❌ |
| 数据陈旧 | `data_stale` | ❌ |
| 同步中 | `sync_in_progress` | ❌ |
| 真实矛盾 | `conflict` → EX-04 | ✅ |
| 无法判定 | `pending_verification` | ❌（转人工） |

### 6.5 无法分类时的人工核实路径

```
判定失败 / 组合未覆盖
  → 记 unclassified（附：三方原值、命中规则版本、缺失的判据）
  → 转 pending_verification 队列
  → 人工核实（客服组长）
  → 核实结论回写为"确认矛盾 / 确认正常 / 数据修正"
  → 该结论进入规则迭代候选池（不改当次判定）
```

**原则**：`unclassified` 与 `pending_verification` **必须存在**；宁可承认不知道，不得硬套类型。

### 6.6 本轮新增发现：第四个数据源（Payment）不在 D-01 范围内

D-01 明确规定 EX-04 是**三方**组合。但 P1 引入 Payment 实体后，出现一类无法被现有规则捕获的矛盾：

| 矛盾 | 例子 | 现规则能否捕获 |
|---|---|---|
| 订单说已支付，支付记录说失败 | `Order.status = paid` + `Payment.status = failed` | ❌ 不在三方矩阵内 |
| 已退款但支付记录无退款流水 | `AfterSale = refunded` + `Payment` 无退款 | ❌ |

**处置状态（V1.1 更新，受 D-09 约束）**：该项为**独立待确认项（清单第 15 项）**，D-09 **未关闭**它，但已排除一个选项：

| 选项 | 内容 | 状态 |
|---|---|---|
| A | V1 不处理支付一致性（保持三方，风险自担） | **仍可选** |
| **B** | 作为 EX-04 的**扩展检查项**（不改"三方"表述，增加一条附加规则） | **仍可选**（V1.0 建议项） |
| C | 新增第 5 类异常 | ❌ **已被 D-09 排除**（"不得新增第 5 类异常"） |

> **D-09 的边界必须写清**：D-09 只做了两件事——(1) 定 `Payment.paid_at` 为起算点；(2) 禁止把支付扩成"第四方"或新增第 5 类异常。它**没有**回答"支付一致性要不要查"。因此 §6.6 的问题从"三选一"缩小为"**A 还是 B**"，但**仍未答**。
>
> **若选 A 的后果**：`Order.status = paid` + `Payment.status = failed` 这类订单会带着**错误的支付前提**进入 EX-01 分析（按 `Payment.paid_at` 起算，而 `Payment` 根本不成功 → 按 D-09-4 实际会被拦在"不判，归待核实"）。**注意**：D-09-4 已经在**入口处**挡掉了这类单子，所以选 A 的实际风险比 V1.0 估计的**小**——但仍不等于"已覆盖"，因为"已退款却无退款流水"这类情形不在 D-09-4 的拦截范围内。

## 8. 审批业务规则

### 8.1 三级的业务含义

| 层级 | 业务含义 | 是否需要审批 | 谁审 |
|---|---|---|---|
| **L0** | 只读、只分析、只建议，不改变任何业务状态 | 否 | — |
| **L1** | 标准风险：方案会被用于对外沟通，但动作可逆 | 是 | **组长** |
| **L2** | 高风险：涉及资金、地址、对外承诺，或数据可信度已受损 | 是 | **主管** |

> **V1.1 更新**：L1 = 组长、L2 = 主管 已由 **D-11** 正式确认（V1.0 时为"沿用 P0-004"的推定）。同时 D-11 确认 V1 用**模拟审批白名单**实现审批人识别——不接真实审批系统、不做 SSO、不做强身份、不做代签。
>
> **"模拟"的含义要说清**：模拟的是**审批人身份的来源**（从白名单取 `operator_id` + 角色），不是模拟审批**行为**。审批动作本身（批准/驳回/要求修改）仍是真实的人工决定，只是人不在真实审批系统里点。

### 8.2 动作分级（沿用 P0-004 §5，补业务说明）

| 动作 | 层级 | 业务理由 |
|---|---|---|
| 异常分析、知识检索 | L0 | 只读产出 |
| 客户回复草稿**生成** | L0 | 生成不等于发出 |
| 客户回复草稿**认定可对外** | **L1** | 一旦对外即产生承诺风险 |
| 标准处理方案（催单、物流查询、补发申请草稿） | **L1** | 会被用于对外沟通 |
| 高风险方案（退款、赔付、改地址、取消） | **L2** | 涉及资金/不可逆 |
| 三方状态矛盾处置 | **L2** | 判据本身不可信（D-06 业务含义） |
| 修改后重新提交 | **同原层级，不降级** | 防"审一次改到底" |
| 写批准记录、写审计 | 系统动作 | 非人工审批 |

### 8.3 草稿的"三态"，务必区分

| 状态 | 含义 | 谁决定 | V1 能否达到 |
|---|---|---|---|
| `draft` | 已生成，仅供内部看 | Service（L0） | ✅ |
| `cleared_for_outbound` | 认定可对外（**仍不发送**） | 组长（L1） | ✅ |
| `sent` | 已发送给客户 | —— | ❌ **V1 禁止** |

> **V1 只能到第二态。** "已发送"不是"没做"，而是"**明确不做**"（P0-002 Won't）。若将来放开，需先补"发送失败/重复发送/撤回"的业务规则。

### 8.4 修改后的审批关系

| 项 | 规则 |
|---|---|
| 次数上限 | 1 次（常量，不可配置放宽） |
| 原草稿 | 标 `superseded`，**保留不删** |
| 新草稿 | 新 `draft_id` + 版本号，`parent_draft_id` 指向原稿 |
| 是否重新审批 | **必须**，且**不继承**旧结论 |
| 层级 | 同原层级；若动作类型升级（如补发→退款）→ 随之升 L2 |
| 超限 | `approval_phase = exhausted`，仅剩批准/驳回 |

### 8.5 五种审批结局（V1.1：超时一项按 D-11 更正）

| 结局 | 系统行为 | 业务含义 |
|---|---|---|
| **批准** | 写批准记录；`status=completed`；**不执行**任何业务动作 | 方案可用于人工执行 |
| **驳回** | `status=failed`；草稿保留 | 方案不被接受 |
| **要求修改** | `approval_phase=waiting_revision`；原稿 `superseded` | 给一次改正机会 |
| **超时（> 24h）** | **`status=failed`**；`approval_expired=true`；`approval_phase` **退出等待**；**不自动批准、不自动驳回、不自动升级**；须重新发起（**推导规则，D-11 第 4 条，尚待确认**） | 不伪造人工决定 |
| **审批端不可用** | 不产生审批结论；任务保持等待；可重试 | **fail-closed：宁可卡住，不得放行** |

> **V1.1 更正记录（必须保留）**：本表"超时"行在 V1.0 写的是"`approval_expired=true`；**状态不自动推进**；须重新发起"。**D-11 明确规定"超时进失败态"**，与"状态不自动推进"不一致。**以 D-11 为准**，本行已改为 `status=failed`。
>
> 这一处不是措辞差异：`status` 停在 `waiting_for_approval`（V1.0 口径）意味着任务**仍活着**，可能被后续审批激活；`status=failed`（D-11 口径）意味着任务**已终结**，任何迟到的审批结果都不能复活它。两者对"迟到结果如何处理"的答案完全相反。

**审批 TTL 的取值与口径（D-11 已确认）**：

| 项 | 值 | 说明 |
|---|---|---|
| TTL | **24 小时** | 常量，不得实现为可延长/可调 |
| 起算点 | 审批请求**创建时刻** | D-11 未单独表述，按必要配套定义记录；若负责人另有定义须在 P2 前更正 |
| 超时判定 | `elapsed >= 24h` | 与 T1/T2/T3 统一的 `>=` 口径（该口径本身仍待确认，见清单第 3 项） |
| 超时后恢复 | **必须重新发起**（新请求、新 TTL）；旧请求作废，迟到结果不生效 | **由 D-11 推导**，非原文；尚需负责人确认 |

> **注意"`>=` 口径"这一行**：TTL 用 `>=` 是本文的一致化建议，**并非 D-11 明文**。D-11 只给了 24h 这个数。若清单第 3 项最终定为 `>`，此处须同步——这是三个参数与审批 TTL 共享同一口径的连带点。

**五种结局的两条不变量（V1.1 补）**：

1. **任何结局都不执行真实业务动作**（D-04 硬约束）——包括"批准"。批准只产生记录。
2. **任何结局都不得由系统代填**——超时不能填"通过"，不可用不能填"驳回"。系统只能记录"没有结论"。

> **fail-closed 是本节最重要的一条**：知识库不可用可以降级（`partial_success`），但**审批不可用不能降级为"免审批"**。二者不可类比。

## 9. 一线客服的完整操作流程（12 步）

| # | 步骤 | 输入 | 执行角色 | 输出 | 失败情况 | 可重试 | 人工介入 |
|---|---|---|---|---|---|---|---|
| 1 | 输入订单号 + 问题描述 | 订单号、自然语言描述 | 客服（人） | 查询请求 | 订单号格式错 / 为空 | 是（改输入） | 否 |
| 2 | 验证输入 | 查询请求 | 系统（入口校验） | 规范化请求 | 订单不存在（SC-057） | 是 | 仅在客服坚持时 |
| 3 | 识别任务并分解 | 规范化请求 | **Coordinator** | 计划 DAG | 计划非法（校验不过） | 是（重新规划，限次） | 否 |
| 4 | 查询订单/支付/物流/售后事实 | 订单号 + `as_of` | **Data Agent**（经 DataPort） | 只读聚合视图 + 完整性标记 | 实体缺失 / 数据陈旧 / 同步中 | 是（1 次） | 缺失严重时转人工 |
| 5 | 检索 SOP 与历史案例 | 异常候选 + 订单上下文摘要 | **Knowledge Agent** | 引用片段 + 来源 + 命中态 | `no_hit` / `unavailable` | 是（1 次） | 否 |
| 6 | 判断异常 | Data + Knowledge 的返回 | **Analysis Agent** | 异常记录（类型/主次/证据） | 无法归类 → `unclassified` | 否（不可重复猜） | 是（转核实） |
| 7 | 汇总异常与证据 | 异常记录集 | **Coordinator** | 1 主 + N 关联 + 摘要 | 归并冲突 | 否 | 否 |
| 8 | 生成方案与回复草稿 | 摘要 + 引用片段 | **Service Agent** | 草稿（`draft_id`） | 生成失败 | 是（1 次） | 否；失败不得出空稿 |
| 9 | 判定审批层级 | 草稿内含动作类型 | **Coordinator**（按规则表） | L0/L1/L2 | 层级判定歧义（多动作取最高） | 否 | 是（歧义时升级） |
| 10 | 形成最终处理建议 | 草稿 + 审批结论 | Coordinator | 建议 + 依据 + 不确定性 | 审批超时/不可用 | 等待 | 是 |
| 11 | 保存审计记录 | 全链路事件 | 系统 | 审计流水 | 写入失败 | 是 | 是（审计不可丢） |
| 12 | 展示结果 | 建议 + 证据 + 状态 | 系统 → 客服 | 界面结果 | 渲染失败 | 是 | 否 |

**四条流程纪律**：

1. **每一步的角色是"谁做决定"，不是"调了哪个工具"**——第 3、7、9、10 步同属 Coordinator，但职责完全不同（规划 / 归并 / 分级 / 汇总）。
2. **第 6 步不可重试**：异常判定重试等于"换个答案再试"，会破坏可追溯性；失败只能转人工。
3. **第 11 步审计写入失败时不得静默继续**：审计是 Gate 0 的验收项之一。
4. **第 8 步失败不得输出空草稿**（D-07-9）：宁可任务失败。

### 10.1 P1-002 新增的三处验收盲区（G-12 ~ G-14）

三项决策解决了规则问题，**但都制造或暴露了新的"规则已定、场景没有"的缺口**。这类缺口比"规则没定"更危险——因为它看起来已经完成。

| # | 缺口 | 来源决策 | 为什么危险 | 处置 |
|---|---|---|---|---|
| **G-12** | "同步事件不得刷新 EX-03"**无已批准场景** | D-10 | 唯一对应场景 SC-083 是**候选未批准**。若实现时把同步算更新，EX-03 永不触发，而**没有任何已批准用例会发现** | ✅ **载体已批准（D-14）**：SC-083 为 G-12 载体，**仍为候选、未入基线**。需同时补"存在较早事实事件"前提（否则按字面应得 `data_missing`） |
| **G-13** | L1 组长 / L2 主管的**角色映射无场景** | D-11 | SC-073/074 均为 L1；L2 无独立场景（承接 P1-001-04 的 G-3）。D-11 把"谁审"定死了，但**没有用例验证 L2 真的走主管** | ✅ **载体已批准（D-14）**：SC-086 为 G-13 载体，**仍为候选、未入基线**。断言须含"角色=主管"+"白名单外不可审批" |
| **G-14** | "支付时间偏离记证据"**无场景** | D-09 | 该动作是 D-09-3 的强制项，但 82 场景中无一条构造"两处 `paid_at` 不一致"。缺了它，偏离记录写没写、写对没写对，验收时看不出来 | ✅ **已批准（D-14）+ P1-003 更正**：**补充 SC-018 的输入条件 + 2 条断言**（不新增编号）。原"受清单 15 约束、暂缓"的处置**理由有误**，见下方说明 |

> **G-14 处置的更正说明（P1-003）**：P1-002 曾把 G-14 挂到"清单第 15 项（支付一致性范围未定）"上，据此判"暂不处置"。这个挂靠是**错的**：
>
> - **D-09-3** 要求"两者不一致时把不一致记为偏离证据"，这是**无条件**的强制动作，只要执行 EX-01 就要做；
> - **清单第 15 项**问的是"支付一致性要不要作为 **EX-04 的附加检查项**"，即**要不要据此判异常**；
> - 二者是"记录"与"判定"两回事。**记录不需要等判定范围定下来。**
>
> 更正后的处置：**补充 SC-018**（168h 且无物流单 → 命中 EX-01）的输入条件为"且 `Order.paid_at` 比 `Payment.paid_at` 晚 2h"，追加两条断言：① `elapsed` 仍按 `Payment.paid_at` 计算（168h，不是 166h）；② 证据中含两者原值与差值。**不新增场景编号，82 不变。**

> **V1.3 补充：三项缺口的状态必须分三层写（D-14）**
>
> | 层 | G-12 | G-13 | G-14 |
> |---|---|---|---|
> | ① 载体是否已批准 | ✅ D-14 | ✅ D-14 | ✅ D-14 |
> | ② 是否已纳入正式基线 | ❌ SC-083 仍候选 | ❌ SC-086 仍候选 | ✅ **SC-018 本就在基线内**（属补充断言） |
> | ③ 是否已执行并留结果 | ❌ | ❌ | ❌ |
>
> **D-14 的原文约束**："三项验收条件齐备**不等于**测试通过；实际执行结果必须单独记录。"
>
> **因此本节不能写"G-12/G-13/G-14 已关闭"**——准确表述是"**三项缺口都已确定用哪条场景验、验什么、怎么算失败；三条场景一条都没跑**"。
