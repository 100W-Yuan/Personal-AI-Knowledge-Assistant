## 1. 五类实体的定位

| 实体 | 一句话定位 | 在 V1 中的角色 |
|---|---|---|
| **Order 订单** | 交易的主键与业务归属锚点 | 聚合入口；其"对外呈现状态"是**派生值** |
| **Payment 支付** | 支付事实的唯一来源 | 提供"是否支付成功"与"何时支付成功" |
| **Shipment 物流**（含 TraceEvent 轨迹事件） | 货物移动事实的唯一来源 | 提供揽收、中转、派送、签收等事实 |
| **AfterSale 售后** | 售后与资金退回事实的唯一来源 | 提供退款/退货状态，是排除条件与矛盾判定的一侧 |
| **WorkOrder 工单** | **人**处理某订单异常的过程载体 | 承载处理过程、结论引用、审批引用 |

> **关键区分**：`WorkOrder` 是**业务实体**，`Task` 是**系统执行单元**。前者是"客服在处理哪件事"，后者是"系统跑了哪一段流程"。一个 WorkOrder 可对应多个 Task（多次检测、多次重试），但 V1 不把 Task 暴露给一线客服。

## 2. 实体关系

```
                    ┌─────────────┐
                    │   Order     │  ← 业务归属锚点（1）
                    └──┬──┬──┬──┬─┘
          1:0..1 │     │  │  │  │ 1:0..N
                 ▼     │  │  │  └──────────────┐
        ┌──────────┐   │  │  │                 ▼
        │ Payment  │   │  │  │          ┌─────────────┐
        └──────────┘   │  │  │          │  WorkOrder  │
                       │  │  │          └──────┬──────┘
            1:0..1     │  │  │ 1:0..N          │ N:1
                       ▼  │  ▼                 ▼
              ┌──────────┐ │ ┌──────────┐  ┌──────────┐
              │ Shipment │ │ │ AfterSale│  │ Operator │
              └────┬─────┘ │ └──────────┘  └──────────┘
                   │ 1:N
                   ▼
            ┌─────────────┐
            │ TraceEvent  │
            └─────────────┘
```

| 关系 | 基数（V1 建议） | 说明 | 状态 |
|---|---|---|---|
| Order–Payment | 1 : 0..1（**生效支付**） | 允许历史上多条支付尝试，只有"成功"的那条为生效支付 | 建议 |
| Order–Shipment | 1 : 0..1 | V1 假设**单包裹**；拆包/多包裹属 Should，V1 不做 | 建议（拆包待确认） |
| Shipment–TraceEvent | 1 : 0..N | 轨迹事件只属于一个物流单 | 建议 |
| Order–AfterSale | 1 : 0..N（**活跃至多 1 条**） | 历史可多条，同一时刻至多 1 条活跃售后 | 建议 |
| Order–WorkOrder | 1 : 0..N | 一个订单可被多次处理 | 建议 |
| WorkOrder–Operator | N : 1 | 一个工单归属一个发起人（一线客服） | 建议 |
| WorkOrder–Task | 1 : N | 系统执行单元，不对外暴露 | 建议 |

**待确认（第 12 项，本轮新增）**：同一订单是否允许**并发多个未关闭**的 WorkOrder？建议 V1 限制为 1 个活跃 WorkOrder，避免重复处理。

## 3. 真相源矩阵（本文件最核心的一张表）

> 方案 C 的核心不是"有视图"，而是**每一项业务事实只有一个来源**。凡不能追溯到源实体的字段，都属派生，**不得作为判定依据**。

| 业务事实 | 唯一真相源 | 派生信息（**不可**单独作为判定依据） |
|---|---|---|
| 是否支付成功 | `Payment.status == success` | `Order.status == paid`、`Order.paid_at` |
| **支付成功时间** | **`Payment.paid_at`**（**D-09 已确认**） | `Order.paid_at`（同步副本，可能滞后；**不得作起算点**） |
| 是否已揽收 | `TraceEvent` 中存在 `picked_up` 及之后事件 | `Order.shipping_status`、`Shipment.status` |
| 当前物流位置/节点 | 最新有效 `TraceEvent` | 同上 |
| 是否已签收 | `TraceEvent` 中存在 `delivered` | 同上 |
| 是否存在退款 | `AfterSale.status ∈ {approved, returning, refunded}` | `Order.status == refunded` |
| 订单是否关闭 | `Order.status == closed`（订单域自身事实） | — |
| 命中哪类异常、谁是主异常 | **不是实体字段**，是 Analysis Agent 签发的 `Anomaly` 记录 | 任何视图上的"疑似异常"标记 |
| 处理过程与结论 | `WorkOrder` | 任何缓存/看板快照 |

> **"支付成功时间"这一行的状态与其他行不同**：其他行的真相源归属是**本文的业务推理**（L-B 级），而这一行已由 **D-09** 正式确认（L-C 级）。区别是实质性的——前者可在 P2 讨论中调整，后者调整需重开决策。

### 3.1 由此得到一条重要推论

`Order.status` 本质是**由 Payment / Shipment / AfterSale 推导出的对外呈现状态**。因此：

> **EX-04 的实质，是"派生层与真相源层的偏离检测"。**

- `Order.status = delivered`（派生）vs 物流无签收事件（源）→ 偏离 → C-02；
- 售后已 `refunded`（源）vs `Order.status = shipped`（派生未更新）→ 偏离 → C-05。

**这也解释了 D-06 为什么把 EX-04 排在最高优先级**：它不是"某一环出了异常"，而是"**派生逻辑本身错了**"。派生层错了，所有基于 `Order.status` 的后续判断都不可信——包括 EX-01 的排除条件（"已取消/已退款则排除"）也可能失效。

## 4. 派生信息的使用规则

| 规则 | 内容 |
|---|---|
| R-D1 | 派生字段**可用于展示与排序**，不得单独用于判定命中/排除 |
| R-D2 | 判定必须回到源实体；源实体缺失时执行 §6 的拒判规则 |
| R-D3 | 派生字段与源实体不一致时，**以源实体为准**，并把不一致本身记为证据（可能是 EX-04） |
| R-D4 | 聚合视图不得新增"只有视图才有"的派生结论（如"疑似异常"）——该结论只能来自 Analysis |

**R-D3 的一个直接应用（EX-01 起算点）—— 已由 D-09 确认为正式规则**：

> EX-01 的 72h **必须**从 **`Payment.paid_at`** 起算，不得从 `Order.paid_at` 或"`Order.status` 变为 `paid` 的时刻"起算。

**理由**：后两者是同步结果，可能延迟；用它们会**人为缩短**已支付时长 → **系统性漏报**。这是判定式级别的偏差，不是精度问题。

**D-09 的六条约束（V1.1 回填，原文照录）**：

| # | 约束 | 对本文件的含义 |
|---|---|---|
| 1 | `Payment.paid_at` 是唯一真相源，72h 只能从它起算 | §3 真相源矩阵该行升为 L-C 级 |
| 2 | `Order.paid_at` 是派生值，**不得**作起算点、不得参与 `elapsed`、不得回填 | §4 R-D1/R-D2 在此行的具体化 |
| 3 | 两者不一致时以 `Payment.paid_at` 为准，并**把不一致记为偏离证据** | R-D3"以源为准 + 记证据"的落地 |
| 4 | `Payment` 缺失 / 非成功 / `paid_at` 为空 → **不判 EX-01**，归 `pending_verification` | 见 §6 修订 |
| 5 | 偏离**只作证据**，不得据此直接判 EX-04 | 与 §3.1 的 EX-04 推论**划清边界** |
| 6 | T1=72h 不变；只解决"从哪个字段起算" | 不改 D-02，不改 T2/T3 |

**两处必须写明的边界**：

1. **"记偏离证据"不等于"判异常"**。`Order.paid_at != Payment.paid_at` 可能只是同步延迟（D-08），应归 `data_stale` 或 `pending_verification`，**不得**直接判 EX-04。支付一致性是否纳入 EX-04 的附加检查项，**仍未定**（清单第 15 项；D-09 只排除了"新增第 5 类异常"这个选项）。
2. **D-09 不改"三方"表述**。EX-04 仍是订单 / 物流 / 售后三方组合，Payment 不在其中。本文 §3.1 说"EX-04 是派生层与真相源层的偏离检测"，这里的"真相源层"**仅指那三方**，不得扩读为包含 Payment。

> **编号对照**：本项在《P1-001-05 待负责人确认清单》中为**第 12 项**，在《P1-001-01 业务需求分析报告》§11 中为**第 13 项**（两文编号互换，内容同一）。对照表见 P1-001-05 §0。

## 5. 各 Agent 可读范围

| 角色 | 可读实体 | 可读范围 | 禁止 |
|---|---|---|---|
| **Coordinator** | **无** | 仅"结构化摘要"（任务成败、异常类型与主次、是否需审批） | 读任何原始字段（P0-003 §5） |
| **Data Agent** | Order / Payment / Shipment / TraceEvent / AfterSale | 经 DataPort 只读聚合视图，含 `as_of` | 写任何实体；读 WorkOrder 之外的敏感字段 |
| **Knowledge Agent** | **无业务实体** | 只读知识库（SOP/政策/历史案例） | 读订单数据 |
| **Analysis Agent** | **无**（不直接取数） | 只消费 Data / Knowledge 的返回 | 自行取数（P0-003 §2.1 第 2 条） |
| **Service Agent** | **无原始实体** | 只读 Coordinator 转交的上下文摘要 + 知识片段 | 读原始订单/物流字段（防越权取数绕过 DataPort） |
| **Human Approval** | **无原始实体** | 只读被审草稿 + 证据摘要 | 读原始数据表 |
| **WorkOrder** | 由系统写入（非 Agent 自由写） | 承载过程记录 | Agent 不得把"结论"写进 WorkOrder 取代 Anomaly 签发 |

> **注**：Service Agent 越权读数据是常见漏洞。规则是：**它要什么，由 Coordinator 从 Data 的回答里摘要给它**，而不是给它一个 DataPort 句柄。

## 6. 缺失时"必须拒绝判断"的清单

> 核心原则：**"没看到"不等于"没发生"。** 否定性判定（如"未揽收""未更新"）必须建立在**数据完整性可信**的前提下。

| 缺失项 | 必须拒绝的判断 | 仍可进行的判断 | 理由 |
|---|---|---|---|
| **Payment 不存在**（订单未支付或支付记录缺失） | 拒绝 **EX-01**（无法确定起算点）；拒绝任何"已支付"断言 → **归 `pending_verification`**（D-09-4） | 无 | 起算点缺失 → 时长不可算 |
| **Payment 存在但 `paid_at` 为空** | 拒绝 EX-01 → **归 `pending_verification`**（D-09-4） | 无 | 同上 |
| **`Payment.status` 非成功** | 拒绝 EX-01；**不得**因 `Order.status == paid` 就当作已支付（D-09-2） | 可提示"支付状态与订单不一致，待核实" | 派生值不可作依据 |
| **Shipment 完全不存在** | 不判 EX-02 / EX-03 | **可判 EX-01**（未创建物流单是"未发货"的强证据，SC-018） | 否定性证据成立 |
| **Shipment 存在但轨迹为空** | **拒绝 EX-01 / EX-02 / EX-03**（标 `data_missing`） | 仅可提示"疑似未揽收，待核实"（SC-054） | 无法区分"真没动"与"轨迹没回传" |
| **AfterSale 不存在（`none`）** | 不适用（**是合法状态，不是缺失**） | 可正常判定 | P0-004 §3.4 |
| **Order 不存在** | 拒绝全部异常判定 | 无（返回"订单不存在"，SC-057） | — |
| **状态字段为 null** | 拒绝基于该字段的判定 | 其余字段可继续 | 不得用默认值补齐 |
| **数据陈旧（`data_stale`）** | 拒绝用该字段判 EX-04 | 可提示"数据待同步" | D-08 |

> **V1.1 修订说明**：前三行的"拒绝判断"在 V1.0 中只写了"拒绝 EX-01"，语义上容易被实现成"静默跳过"。D-09-4 明确规定**必须归入 `pending_verification`**——"不判"与"不处理"是两件事：前者是不下结论，后者是把单子丢了。**拒判必须有去处**。

### 6.1 "有单无轨迹"为什么不能判 EX-01（本轮补充的规则）

这是容易做错的地方：

| 情形 | 能否判 EX-01 | 为什么 |
|---|---|---|
| 无 Shipment 实体（从未建单） | **能** | 业务上"未发货"是确定事实 |
| 有 Shipment，轨迹为空，**有同步正常证据** | **能** | 确认"没有揽收事件发生" |
| 有 Shipment，轨迹为空，**无同步正常证据** | **不能**（`data_missing`） | 轨迹可能未回传，"看不到"≠"没发生" |

**结论**：EX-01 的成立需要**否定性证据**，而不是"缺乏肯定性证据"。这条规则同样适用于 EX-03。

## 7. 聚合视图能提供什么

| 视图内容（业务概念层） | 是否可由视图提供 | 说明 |
|---|---|---|
| 订单基本信息 + 对外呈现状态 | ✅ | 需标注"派生" |
| 生效支付的成功时间 | ✅ | 从 Payment 投影，只读 |
| 物流状态 + 有效轨迹序列（按 `as_of`） | ✅ | 需标注哪些事件被排除：**预测类、作废类、重复推送、同步快照**（四类均由 **D-10** 批准排除）；视图不得把排除后的序列倒推成"完整轨迹" |
| 售后当前状态 + 类型（`refund_only` / `return_refund`） | ✅ | 类型字段是 C-04/C-05 判定的前提 |
| 完整性标记（缺失/陈旧/同步中） | ✅ | 供 Analysis 走降级分支 |
| **异常类型 / 主次 / 结论** | ❌ **不可** | 只能由 Analysis 签发（P0-004 §4.5） |
| **"建议动作"** | ❌ **不可** | 由 Service 生成草稿 |

**视图的三条硬约束**（沿用 D-03）：只读、不产生独立业务事实、Agent 不得绕过 DataPort 访问实体。
