## 1. 产品定位

**Enterprise Copilot** 是一个面向企业售后场景的 **AI 业务协同与异常处理平台**。

它要解决的问题不是"回答客户问题"，而是：

> 当一笔订单在**已支付之后、签收之前**出现停滞、滞留、失联或状态矛盾时，系统能否**自己发现、自己查证、自己形成可执行方案、并把决策权交回人**。

三条定位底线（本版强化，因 D-03/D-04 而更明确）：

1. **不是聊天机器人**。对话只是入口，产出物是"异常工单 + 分析结论 + 可审批方案"。
2. **不是自动化执行系统**。V1 的一切动作止于"已批准方案记录"，不触碰业务系统。
3. **不是单 Agent 套壳**。分析、取数、知识、方案、审批由不同角色承担，且**权限互不越界**。

## 2. 目标用户

| 角色 | V1 是否为系统用户 | 使用方式 | 说明 |
|---|---|---|---|
| **一线客服** | **是——唯一主用户** | 发起查询、查看异常、确认/提交方案、接收"要求修改"意见 | V1 的全部界面与流程围绕此人设计 |
| 组长 | 仅通过审批流程出现 | 审批 L1 方案（批准 / 驳回 / 要求修改） | 不使用主工作台；以 `operator_id` 弱标识参与 |
| 主管 | 仅通过审批流程出现 | 审批 L2 方案（高风险、状态矛盾） | 同上 |
| 知识运营 | 否（V1 不含） | — | 知识维护降为 Should/Won't |
| 系统管理员 | 否（V1 仅审计可查） | 查看审计日志 | 无配置界面 |

**红线**：不得因为引入 L1/L2 审批，就把组长/主管升格为"主用户"。V1 的主用户只有一个。

## 3. 核心场景（唯一闭环）

**已支付订单 · 物流停滞 · 从发现到可审批方案**

```
一线客服发起（订单号）
  → Coordinator 规划
  → Data Agent 取数（只读聚合视图）
  → Knowledge Agent 检索处置依据（SOP / 政策）
  → Analysis Agent 判定异常类型与主次
  → Service Agent 生成处置方案草稿
  → 审批（L0 免审 / L1 组长 / L2 主管）
  → 产出「已批准方案记录」
  → 一线客服人工执行（系统外）
```

**闭环终点是"可审批方案"，不是"问题已解决"。** 这一条决定了 V1 的全部验收口径。

覆盖的 4 类异常（EX-01~EX-04）：未揽收、中转滞留、长时间未更新、三方状态矛盾。判定规则与参数见 P0-004。

### 3.1 异常优先级（D-06，已确认）

> **EX-04 > EX-01 > EX-02 > EX-03**

| 异常 | 为何排在前面（业务含义，非数值推导） |
|---|---|
| EX-04 三方状态矛盾 | 判定基础不可信，先修数据再看别的 |
| EX-01 已支付未揽收 | 业务处理窗口较短 |
| EX-02 中转滞留 | 需跟进物流推进 |
| EX-03 长时间未更新 | 兜底异常 |

**用户可见的行为承诺**（由此产生，属 V1 可验收内容）：

1. 同一订单、同一检测周期，**页面上只有一个"主异常"**，其余以"关联异常"列出；
2. 关联异常**不会因为不是主异常而消失**，证据可查看；
3. 优先级**不改变**任何异常的触发条件——命中就是命中，只是排序不同。

## 4. V1 范围边界

### 4.1 Must（12 项，V1 必须交付）

| 编号 | 能力 | 备注 |
|---|---|---|
| M-01 | 订单异常查询入口（按订单号发起） | 单轮任务，非多轮闲聊 |
| M-02 | 只读订单聚合视图查询（经 DataPort） | D-03 |
| M-03 | EX-01 识别（T1=72h） | D-02 |
| M-04 | EX-02 识别（T2=48h） | D-02 |
| M-05 | EX-03 识别（T3=72h） | D-02 |
| M-06 | EX-04 识别（三方状态组合判定） | D-01，枚举待确认 |
| M-07 | 知识依据检索与片段引用（含无命中/不可用降级） | — |
| M-08 | 多异常主次判定与归并（**1 主 + N 关联**，优先级 EX-04>EX-01>EX-02>EX-03） | D-06，规则见 P0-004 §4 |
| M-09 | 处置方案草稿生成（含客户回复草稿） | 草稿≠发送 |
| M-10 | L0/L1/L2 审批（批准/驳回/要求修改/超时；`approval_phase` 三态） | D-04、D-07 |
| M-11 | 要求修改后重新提交（最多 1 次，新 `draft_id`，必重新审批） | US-13、D-07 |
| M-12 | 全链路审计（事件可追溯、幂等可验证） | — |

### 4.2 Should（V1 不承诺，若有余量再议）

- 批量订单巡检（一次查多单）
- 异常趋势看板
- 知识运营后台（SOP 上传/编辑）
- 管理员配置界面（阈值可视化调整）
- 同城中转 vs 跨省中转的差异化 T2
- 节假日/大促阈期豁免
- 会签审批（多角色同时审）
- 审批人缺席自动升级上级
- `promised_ship_at`（商家承诺发货时间）作为 T1 起算点

### 4.3 Won't（V1 明确不做，且不视为缺陷）

| 不做的事 | 原因 |
|---|---|
| 连接真实 OMS/WMS/TMS/CRM | 既定决策：本地模拟数据 |
| 真实退款、补发、改地址、取消订单 | D-04：V1 禁止一切真实业务写操作 |
| 自动向客户发送消息（短信/IM/邮件） | D-04 明列禁止 |
| 多轮自由对话式追问 | 与"任务型闭环"定位冲突，V1 只做单轮任务 |
| 企业 SSO / 数字签名 / 强身份 | V1 用 `operator_id` 弱标识，不主张身份可信 |
| 跨租户隔离 | 单租户本地环境 |
| 模型微调 / 私有化部署 | 不在 P0 范围 |
| 承诺赔付、承诺时效等对外承诺生成 | 属 L3 风险，V1 无对应层级 |

## 5. 与相邻系统的行为级差异

| 维度 | 聊天机器人 | 工单系统 | **本产品（V1）** |
|---|---|---|---|
| 触发 | 用户提问 | 人手工建单 | 人给订单号，系统**自行判定是否异常** |
| 信息获取 | 依赖用户描述 | 依赖人工填单 | 多 Agent 分工取数 + 查知识，**结论带依据** |
| 产出 | 一段话 | 一张待办 | **异常结论 + 主次 + 方案草稿 + 审批记录** |
| 决策权 | 无 | 人 | 系统给建议，**人做审批** |
| 可追溯 | 通常无 | 有工单流水 | 事件级审计（含 Agent 分工与审批路径） |
| 出错时 | 说错话 | 单子填错 | **降级并声明缺失**，不猜 |

## 6. 安全与数据边界（V1 硬约束）

### 6.1 数据分级

| 级别 | 内容 | V1 处理 |
|---|---|---|
| L0 公开 | 通用物流常识、公开政策 | 可入知识库 |
| L1 内部非敏感 | 订单号、物流单号、状态、时间 | 可用于模拟数据与检索 |
| L2 PII | 姓名、手机号、详细地址 | **模拟数据一律伪造**；不进入提示词的可识别形态 |
| L3 敏感凭据 | 密钥、Token、支付凭证 | **V1 完全不接触**，不读取 `.env` |

### 6.2 五条硬声明

1. **不连接真实企业系统**：全部数据来自本地只读模拟数据集。
2. **不执行真实业务写操作**：无退款、无补发、无改址、无对外消息。
3. **审批通过 ≠ 业务已执行**：审批通过只产生"已批准方案记录"+ 草稿状态流转。
4. **不向未获批准的外部服务发送敏感信息**：V1 不引入任何外部业务服务。
5. **数据缺失不猜**：区分"无命中 / 不可用 / 数据缺失"三态，分别降级，不合成一个"未找到"。
