## D-06 异常优先级：accept

**决策**：负责人明确选择 `accept`。异常主次优先级固定为：

> **EX-04 > EX-01 > EX-02 > EX-03**

**业务含义（原文）**：

| 异常 | 含义 |
|---|---|
| EX-04 | 三方状态矛盾，判定基础不可信，优先处理 |
| EX-01 | 已支付但未揽收，存在较短的业务处理窗口 |
| EX-02 | 中转滞留，需要跟进物流推进 |
| EX-03 | 长时间未更新，作为兜底异常 |

**实施约束（六条，原文）**：

1. 一个订单同一检测周期只产生**一个主异常**；
2. 其他命中的异常作为**关联异常保留，不得直接丢弃**；
3. 优先级**只决定主异常**，不改变各异常自身的检测条件；
4. **不得**仅依据 T1/T2/T3 数值推导优先级；
5. 同一检测周期的异常归并**必须保持幂等**；
6. Analysis Agent 负责**签发**异常结果，Coordinator 负责**归并和汇总**，不得自行创造异常事实。

**状态**：优先级本身已确认；"同一检测周期"的周期长度、关联异常的持久化形态仍属 P2 设计，未确认。

## D-07 `revision_required` 表示方案：marker

**决策**：负责人明确选择 `marker`（修订标记），**不新增独立任务状态 `revision_required`**。

**设计（原文）**：

- `status` 保持 `waiting_for_approval`；
- 新增 `approval_phase` 表示审批阶段；
- 阶段候选值：`waiting_decision` / `waiting_revision` / `exhausted`。

| 取值 | 语义 |
|---|---|
| `waiting_decision` | 等待审批人批准或驳回 |
| `waiting_revision` | 审批人要求修改，等待生成新版本草稿 |
| `exhausted` | 修改次数已达上限，不允许再次要求修改 |

**约束（十条，原文）**：

1. 不新增独立任务状态 `revision_required`；
2. 最多允许要求修改**一次**；
3. 原草稿保留，不覆盖、不删除；
4. 修改后生成**新的 `draft_id` 和版本号**；
5. 新草稿**必须重新发起审批**；
6. **不继承**旧审批结论；
7. 审批通过只生成批准记录，**不代表业务操作已执行**；
8. 审批重复请求**必须幂等**；
9. 修改失败**不能生成空草稿**；
10. 检查 `approval_phase` 与现有状态机、AC-S7、US-13 的一致性。

**边界**：具体字段结构、事件字段、持久化结构**仍须遵守 P2 设计阶段边界**，不得提前建表或改代码。

## D-09 EX-01 起算点：取 `Payment.paid_at`（采用 A）

**决策**：负责人明确选择 **A**。EX-01（已支付未揽收，T1=72h）的起算点**唯一取 `Payment.paid_at`**。

**真相源声明**：

| 业务事实 | 唯一真相源 | 派生值（不可作起算点） |
|---|---|---|
| 支付成功时间 | **`Payment.paid_at`** | `Order.paid_at` |

**约束（六条）**：

1. `Payment.paid_at` 是"支付成功时间"的**唯一真相源**；EX-01 的 72h **只能**从它起算。
2. `Order.paid_at` 是**派生同步值**：不得作为起算点，不得参与 `elapsed` 计算，不得在 `Payment.paid_at` 缺失时用于回填。
3. 两者**不一致时**：以 `Payment.paid_at` 为准，并**把不一致本身记为偏离证据**（进入异常证据，不得只打日志后丢弃）。
4. `Payment` 缺失、`Payment.status != success`、或 `paid_at` 为空时：**不判 EX-01**，归入**待核实**（`pending_verification`）；**不得**静默跳过，**不得**用 `Order.paid_at` 补位。
5. `Order.paid_at` 与 `Payment.paid_at` 的偏离**只作为证据**，**不据此直接判 EX-04**；时间差可能只是同步延迟（D-08），应归 `data_stale` 或 `pending_verification`。
6. D-02 的 **T1=72h 数值不变**。本决策只解决"从哪个字段起算"，**不改任何阈值、不改 T2/T3**。

**与 EX-04 的关系（须明确，但不得改三方定义）**：

- D-01 已规定 EX-04 是**订单 / 物流 / 售后三方**组合判定。本决策**不得**把支付扩为"第四方"，**不得**修改"三方"表述，**不得**新增第 5 类异常。
- "订单声称已支付、支付记录为失败或无记录"这类矛盾的**处置方式仍未定**（是否作为 EX-04 的附加检查项）。该项在 P1-001-05 中为第 15 项，**本轮未关闭**。
- **明确禁止**：把 `Order.paid_at != Payment.paid_at` 直接判为 EX-04 命中。

**影响**：取派生值会**系统性缩短**已支付时长 → 漏报 EX-01；本决策消除了该漏报路径。同时新增一项强制动作——**支付时间偏离必须留证**（该动作目前无已批准场景覆盖，见 P1-002 报告 G-14）。

## D-11 审批时效与审批人：TTL 24h / 超时进失败态 / 模拟审批白名单（采用 A）

**决策**：负责人明确选择 **A**。

| 项 | 已确认值 |
|---|---|
| 审批请求 TTL | **24 小时** |
| TTL 起算点 | 审批请求**创建时刻**（见下方说明） |
| 超时后果 | 任务进入**失败态**（`status = failed`），并置 `approval_expired = true` |
| 是否自动批准 | **否** |
| 是否自动驳回 | **否** |
| 审批人来源 | V1 用**模拟审批白名单**（不接真实审批系统、不做 SSO / 强身份） |
| L1 审批人 | **组长** |
| L2 审批人 | **主管** |
| 审批端不可用 | **不得绕过**（fail-closed） |

> **起算点说明**：D-11 确认了"TTL = 24h"，但未单独表述起算点。没有起算点则 TTL 不可执行，故按"**请求创建时刻**"作必要配套定义；若负责人另有定义，须在 P2 前更正。

**硬约束（八条）**：

1. TTL 固定 **24h**，是**常量**；不得实现为"可自动延长"或"按操作人可调"。
2. 超时**只**产生"失败 + 已过期标记"，**不产生任何审批结论**。
3. **不得**把超时当默认通过，**也不得**把超时当默认驳回——两者都是伪造一个不存在的人工决定。
4. 超时后若需继续处理，**必须重新发起审批**（新请求、新 TTL）；旧请求作废，**迟到的审批结果不直接生效**。
   > **区分**：第 1~3 条为 D-11 **原文确认**；第 4 条由"超时进失败态 + 不自动批准"**推导**得出，作为配套规则记录，**尚需负责人确认**，不得当作已签字条款。
5. 模拟审批白名单只解决"**谁有权审批**"，**不改变** D-04 的 L0/L1/L2 分级，**不改变**"审批通过只写记录、不执行业务动作"。
6. **审批端不可用时不得降级为免审批**：知识库不可用可降级（`partial_success`），审批不可用只能等待或失败。二者不可类比。
7. 审批人身份以 `operator_id` + 角色（组长 / 主管）记录；**不做**强身份认证、SSO、代签。
8. 本决策**不涉及**：审批通知渠道、审批意见富文本、多级会签、代理人机制——均属 V1 之外。

**与既有文档的一处冲突（已按本决策更正）**：P1-001-01 §8.5 原写"超时 → `approval_expired=true`；**状态不自动推进**；须重新发起"，与本决策"**超时进失败态**"不一致。**以 D-11 为准**，原表述已在 P1-002 更正为"进入 `failed`"。
