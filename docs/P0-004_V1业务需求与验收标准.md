## 2. 四类异常定义

| 编号 | 名称 | 判定式（建议口径） | 排除条件 |
|---|---|---|---|
| **EX-01** | 已支付未揽收 | `order.paid == true` 且 物流无"已揽收"及之后节点 且 `now − paid_at ≥ 72h` | 订单已取消/已关闭/已退款 |
| **EX-02** | 中转滞留 | 最后一条"有效中转节点"轨迹时间 `t_hub` 满足 `now − t_hub ≥ 48h` 且其后无推进节点 | 已签收、已退回、已关闭 |
| **EX-03** | 长时间未更新 | `now − max(有效轨迹时间) ≥ 72h` | 已签收、已关闭/退款 |
| **EX-04** | 三方状态矛盾 | 订单/物流/售后三方状态组合落在**非法组合集**内（见 §3） | 数据缺失、陈旧、同步中、无法判定（见 §3.4 四态） |

**判定顺序（强制）**：先判缺失 → 再判"同步中" → 再判是否"无法判定/待核实" → 再判 EX-04（组合）→ 再判 EX-01/02/03（时间）→ 最后按 D-06 归并主次。

> **EX-02/EX-03 的事件口径（P1-004 / D-12 + D-15 补充，V2.3）**
>
> 上表判定式中的"**推进节点**""**有效轨迹**"，其事件归属已由 **D-12** 批准：
>
> | 规则 | 已批准内容（D-12） | 对上表的影响 |
> |---|---|---|
> | **R-01** | 真实运输推进事件归 **C2**；**状态快照不得仅凭状态名称**直接认定为有效推进；无法确认语义时进 `pending_verification`，不得猜测 | 「推进节点」不含同步刷新/预测/重复/未确认快照 |
> | **R-02** | 物流 `exception` **独立为第 8 类**：**可刷新 `t_last`，但不构成推进** | EX-03 的 `max(有效轨迹时间)` **含**异常事件；EX-02 的"无推进节点"**不含**异常事件 |
> | **R-03** | 有效 C1 被作废时，`t_hub` **回退至上一条仍有效 C1**；无则按"从未进入有效中转"处理 | 见 SC-027 |
>
> **D-15 的职责分工（已接受的设计安排，不是缺陷）**：真实离站推进后，**EX-02 在该路径上不再适用**，由 **EX-03** 承接长时间无更新识别；**T2=48h / T3=72h 不变**。
> **表述纪律**：不得写成"系统失去异常检测能力"或"静默漏报"——这是**有意的异常分类分工**。
>
> **仍未定的部分**：数据源侧的**事件枚举字典与接口样例**（属 L-A 层）。D-12 明确本次批准"**不代表已与任何真实物流平台事件字典完成映射验证**"。
理由：① 状态矛盾会污染所有基于状态的时间判定，必须先解决可信度问题；② 无同步信号时不得把时间差当矛盾（D-08-2）。

## 3. EX-04 三方状态组合矩阵（D-01 落地）

### 3.1 状态枚举

> ⚠️ **本节枚举全部为建议值。项目内不存在任何企业业务代码或状态定义（P0-001 已核实：业务关键词仅出现在 1 个 RAG 测试夹具的示例文档中）。因此以下枚举属"候选集"，标注为「**待定义**」，不得视为企业真实规则。**

**订单状态（O）**

| 值 | 含义 |
|---|---|
| `created` | 已创建未支付 |
| `paid` | 已支付，未发货 |
| `shipped` | 已发货 |
| `delivered` | 已签收 |
| `completed` | 已完成 |
| `closing` | 关闭中（取消/退款处理中） |
| `closed` | 已关闭 |
| `refunded` | 已退款 |

**物流状态（S）**

| 值 | 含义 |
|---|---|
| `no_shipment` | 无物流单 |
| `pending_pickup` | 待揽收 |
| `picked_up` | 已揽收 |
| `in_transit` | 运输中 |
| `at_hub` | 到达中转 |
| `out_for_delivery` | 派送中 |
| `delivered` | 已签收 |
| `returning` | 退回中 |
| `returned` | 已退回 |
| `exception` | 物流异常（破损/丢失等） |

**售后状态（A）**

| 值 | 含义 |
|---|---|
| `none` | 无售后记录（**不等于数据缺失**） |
| `applied` | 已申请 |
| `reviewing` | 审核中 |
| `approved` | 已同意 |
| `rejected` | 已拒绝 |
| `returning` | 退货中 |
| `refunded` | 已退款 |
| `closed` | 已关闭 |

### 3.2 合法组合（用规则表达，不做 8×10×8 穷举）

| 规则 | 组合 | 说明 |
|---|---|---|
| L-1 | `created` + (`no_shipment`\|`pending_pickup`) + `none` | 支付前 |
| L-2 | `paid` + `pending_pickup` + `none` | 已付待发货（超 T1 才成 EX-01） |
| L-3 | `shipped` + (`picked_up`\|`in_transit`\|`at_hub`\|`out_for_delivery`) + `none` | 运输中 |
| L-4 | (`delivered`\|`completed`) + `delivered` + (`none`\|`applied`\|`reviewing`\|`approved`\|`closed`) | 签收后（含签收后申请售后） |
| L-5 | `refunded` + (`returning`\|`returned`) + (`returning`\|`refunded`) | 退货退款闭环 |
| L-6 | `closed` + `pending_pickup` + (`none`\|`rejected`\|`closed`) | 未发货关闭 |
| L-7 | `refunded` + `delivered` + `refunded`，且 `after_sale.type == refund_only` | **仅退款例外**：货已签收但不退回 |
| L-8 | (`shipped`\|`delivered`) + `exception` + (`applied`\|`reviewing`) | 物流异常本身合法，转异常处理 |

### 3.3 非法组合（= 状态矛盾，命名 C-01~C-06）

| 编号 | 组合 | 业务含义 | 建议严重度 |
|---|---|---|---|
| **C-01** | `paid` + `delivered` | 未发货却已签收（物理不可能） | 高 |
| **C-02** | (`delivered`\|`completed`) + (`pending_pickup`\|`picked_up`\|`in_transit`\|`at_hub`\|`out_for_delivery`) | 订单已签收但物流未签收 | 高 |
| **C-03** | `closed` + (`picked_up`\|`in_transit`\|`out_for_delivery`) | 订单已关闭但货仍在派送 | 高 |
| **C-04** | `refunded` + `delivered` + (`returning`)，且 `after_sale.type == return_refund` | 退货退款但货未退回（矛盾） | 高 |
| **C-05** | 售后 `refunded` 但订单仍为 (`paid`\|`shipped`\|`delivered`)，且 `after_sale.type == refund_only` | 已退款但订单状态未反映 | 高 |
| **C-06** | `paid` + `delivered` + (`returning`) | 三方全矛盾（叠加 C-01） | 最高 |

**C-04 的关键例外**：`refund_only`（仅退款）场景下 `refunded + delivered` 是**合法**（L-7），**不得**判为 C-04。这要求售后记录必须携带 `type` 字段——**该字段是否存在属待定义**，若不存在则 C-04/C-05 无法判定。

### 3.4 四态严格区分：缺失 / 陈旧 / 同步中 / 矛盾（D-08）

> **W1 数值未确定（D-08 = defer）。** 本表不出现任何分钟/小时数值；W1 未定前，**不得**把三方数据的时间差直接判为 EX-04。

| 情形 | 判定依据（不依赖 W1） | 归类 | 可判 EX-04 | 禁止 |
|---|---|---|---|---|
| **实体缺失** | 无物流单 / 无任何轨迹 / 订单不存在 | `data_missing` | **否** | 不得判为矛盾 |
| **字段缺失** | `paid_at` 为 null、状态字段为 null | `data_missing` + 指明字段 | **否** | 不得用默认值补齐 |
| **售后无记录** | `A = none` | **合法状态**，非缺失 | — | 不得归入 `data_missing` |
| **数据陈旧** | 字段 `updated_at` 明显早于 `as_of`（"明显"的量化即 W1，**未定**） | `data_stale` | **否** | 不得用 stale 字段判 C-01~C-06 |
| **数据同步中** | 存在同步动作进行中的信号（状态已变更、下游未反映） | `sync_in_progress` | **否** | 不得当作矛盾 |
| **真实矛盾** | 三方均有值、**无同步信号**、组合落在 C-01~C-06 | `conflict` → EX-04 | **是** | 不得降级为"疑似" |
| **无法判定**（兜底） | 有值差但信息不足以区分延迟与矛盾 | `pending_verification` | **否** | **不得默认判矛盾**（D-08-4） |

**三态到五态的演进**：V2.0 只区分"缺失/矛盾/stale"三态；D-08 明确要求区分**四类**（缺失、陈旧、同步中、真实矛盾），并增加"无法判定"兜底路径 → 本版为 **5 个取值**。

**关键工程结论（不依赖 W1 也可运行）**：`conflict` 的**主判定路径无需 W1** —— 当三方数据由同一批次写入（`updated_at` 一致）且组合非法时，可立即判矛盾。W1 只影响"有值差时能否自动判定"这一支路；W1 未定期间该支路整体走 `pending_verification`（转人工），因此 **V1 可以在没有 W1 的情况下安全运行**，代价是自动化率较低、人工核实量较高。

**W1 待设计五项**（数值 / 起算点 / 适用数据源 / 超时行为 / 与 `as_of` 回溯的关系）见 P0-003 §10.2。

### 3.5 EX-04 判定算法（可审查伪码）

```
1  if 任一实体缺失 or 关键字段为 null:          → data_missing（结束）
2  if 存在同步中信号:                            → sync_in_progress（结束）
3  if 三方 updated_at 不一致（存在值差）:
3a     if 能确认属于同步延迟:                    → data_stale（字段剔除，继续）
3b     else:                                     → pending_verification（转人工，结束）
4  if 剩余字段组合 ∈ L-1..L-8:                   → 正常
5  if 剩余字段组合 ∈ C-01..C-06:                 → EX-04（记录命中的 C 编号）
6  else:                                         → unclassified（转人工，禁止猜测）
```

**相对 V2.0 的变化**：原第 2 步 `updated_at < as_of - W1` 依赖未定的 W1，已改写为不依赖具体数值的**分支 3/3a/3b**。这是 D-08 的直接落地：没有 W1 也能跑，且不会把时间差误判成矛盾。

`unclassified` 与 `pending_verification` 都是**必须存在**的兜底分支：宁可报"未分类/待核实"，不可硬套一个矛盾类型。

## 4. 异常主次关系与重复归并

### 4.1 同一 `as_of` 是否允许多个异常

**建议允许**：1 条**主异常** + N 条**从属异常**，同属一个 `task_id`，以 `is_primary` 与 `related_anomaly_ids` 表达。

理由：强行"一单一异常"会导致信息丢失（如 EX-04 掩盖了 EX-02）；强行"全并列"则使用户无法决策。

### 4.2 主异常判定（**D-06 已确认**）

> **优先级已由负责人确认为 `accept`：EX-04 > EX-01 > EX-02 > EX-03。** 本节不再是建议。

| 优先级 | 异常 | 业务含义（D-06 原文） | 状态 |
|---|---|---|---|
| **P-1** | EX-04 三方状态矛盾 | 判定基础不可信，优先处理 | **已确认** |
| **P-2** | EX-01 已支付未揽收 | 存在较短的业务处理窗口 | **已确认** |
| **P-3** | EX-02 中转滞留 | 需要跟进物流推进 | **已确认** |
| **P-4** | EX-03 长时间未更新 | 作为兜底异常 | **已确认** |

**六条实施约束（D-06 原文，全部为硬约束）**：

| # | 约束 | 落地方式 |
|---|---|---|
| 1 | 一个订单同一检测周期只产生**一个主异常** | `is_primary` 在同一 `(order_id, detection_cycle_id)` 内**有且仅有 1 条**为 true（可断言） |
| 2 | 其他命中异常作为**关联异常保留，不得丢弃** | 全部写入 `related_anomaly_ids`，`is_primary=false`，`evidence` 完整保留 |
| 3 | 优先级**只决定主异常**，不改变检测条件 | 各 EX 的判定式与 T1/T2/T3 **不受**优先级影响；不得因"已判 EX-04"就跳过 EX-02 的检测 |
| 4 | **不得**仅依据 T1/T2/T3 数值推导优先级 | 优先级来自本节固定表，**硬编码常量**，不参与计算 |
| 5 | 同一检测周期的异常归并**必须幂等** | 幂等键见 §4.4；重复归并不新增记录、不改变 `is_primary` |
| 6 | Analysis Agent **签发**，Coordinator **归并汇总**，不得创造异常事实 | 见 §4.5 与 P0-003 §2.2 |

**若同一优先级内命中多个**（如两条 C 编号同时成立）：取 `severity` 高者；仍相同则取 `C-编号` 小者，保证确定性。此规则为**建议**（D-06 未覆盖此细节）。

### 4.3 关联异常记录

| 字段 | 说明 |
|---|---|
| `anomaly_id` | 唯一标识 |
| `task_id` / `order_id` | 归属 |
| `anomaly_type` | EX-01~EX-04 |
| `is_primary` | 同一任务内**有且仅有 1 条**为 true |
| `related_anomaly_ids` | 从属异常互指 |
| `rule_version` | 规则版本（阈值变更时用于回溯） |
| `evidence` | 判定依据（命中的 C 编号 / 关键时间戳） |

### 4.4 重复检索与重复请求

**幂等键（建议）**：`hash(order_id + anomaly_type + rule_version + detection_cycle_id)`

- **不得**把精确 `as_of` 放入幂等键：`as_of` 每次请求都不同，会导致幂等完全失效；
- `detection_cycle_id` 由调度器给定（如"每小时一轮"），同一轮内重复请求 → 命中同一异常记录；
- 不同 `detection_cycle_id` → 允许产生新记录（这是"复查"而非"重复"）。

**请求级幂等**：`correlation_id` 相同 → 直接返回首次结果，不重跑 DAG。

### 4.5 多 Agent 汇总去重（关键设计，D-06-6 落地）

| 规则 | 内容 |
|---|---|
| **单一签发者** | 异常记录**只能由 Analysis Agent 签发**；Knowledge/Data/Service 只能引用 `anomaly_id`，**不得**自行创建异常 |
| **Coordinator 只归并不创建** | 归并 = 排序 + 标记主次 + 合并 evidence；**不产生新异常事实**。Coordinator "顺手补一条异常"属越权 |
| **关联异常不得丢弃（D-06-2）** | 未被选为主异常的记录必须完整保留：`is_primary=false` + `evidence` 原样 + 出现在 `related_anomaly_ids`。**禁止**为"页面简洁"而只存主异常 |
| **同任务内去重** | `(anomaly_type, evidence_hash)` 相同 → 合并，不新增 |
| **归并幂等（D-06-5）** | 同 `(order_id, detection_cycle_id)` 重复归并：不新增记录、不改变 `is_primary`、不重写 evidence；返回与首次相同结果 |
| **跨 Agent 冲突** | 若两个子任务对同一订单给出不同异常集，以 Analysis Agent 的产出为准，冲突记入审计 |

**三条可校验的不变量**：

1. 同一 `(order_id, detection_cycle_id)` 内 `count(is_primary == true) == 1`；
2. 命中 N 类异常时，`len(related_anomaly_ids) + 1 == N`（不允许静默丢失）；
3. 同周期重复归并两次，异常记录集合与 `is_primary` 归属**完全一致**。

## 5. L0/L1/L2 审批动作映射表（D-04 落地）

**前提**：D-04 明确**不设金额门槛**。因此层级**只由动作类型（风险性质）决定**，金额仅作为方案内容展示，不影响层级。

| # | 动作 | 层级 | 审批角色 | V1 允许生成草稿 | V1 允许执行 | 说明 |
|---|---|---|---|---|---|---|

| A-09 | 审计日志写入 | 系统动作 | — | — | 允许 | — |

### 5.1 三条判定规则

1. **层级取动作的"最高风险段"**：一个方案含多个动作时，按其中最高层级审批（如"催单 + 补发"→ L1；"催单 + 退款"→ L2）。
2. **修改稿不因"已审过一次"而降级**（防"审一次、改到底"绕过风控）。
3. **任何动作都不得跳过 L2 直达执行**——V1 不存在执行通道，此规则是冗余保险。

### 5.2 V1 绝对禁止（与层级无关）

真实退款 / 补发下单 / 改收货地址 / 取消订单 / 发送短信·IM·邮件 / 调用任何外部业务 API。

### 6.4 US-13 详版：审批人要求修改最多一次（**D-07 已确认：marker 方案**）

> **D-07 已确认**：`status` 恒为 `waiting_for_approval`，用 `approval_phase ∈ {waiting_decision, waiting_revision, exhausted}` 表达审批阶段；**不新增独立状态**。下表 9 条 AC 即基于该表示写成，无需再作"若选独立状态"的二选一调整。

**故事**：作为一线客服，方案被要求修改时我希望能改一次并重新审批，以便在不绕过风控的前提下避免无限返工。

**Given/When/Then（9 点）**

| # | 覆盖点 | 验收标准 |
|---|---|---|
| 1 | 要求修改 | **Given** 草稿处于 `waiting_for_approval / waiting_decision`；**When** 审批人选择"要求修改"并填写意见（非空）；**Then** `approval_phase=waiting_revision`，意见与该草稿关联，`revision_count` 递增为 1，产生 `approval.revision_requested` |
| 2 | 原计划失效 | **Given** 已进入 `waiting_revision`；**Then** 原草稿 `status=superseded`（**保留、不删除、不覆盖**），**不产生**"已批准方案记录"，原草稿不得再被任何动作引用 |
| 3 | 新草稿生成 | **Given** 存在 `waiting_revision` + 意见；**When** 提交人触发修订；**Then** Service 基于「原草稿 + 修改意见 + 原分析结论」生成**新 `draft_id`**，`parent_draft_id` 指向原草稿，新稿 `status=draft`，**不自动提交审批**，需提交人确认后提交 |
| 4 | 次数限制 | **Given** `revision_count=1`；**When** 审批人**再次**选"要求修改"；**Then** 系统**拒绝**并提示"已达上限（1 次）"，`approval_phase=exhausted`，此时仅剩"批准/驳回"，产生 `approval.revision_denied_limit`。上限为常量 1，**不得配置化放宽** |
| 5 | 是否重新审批 | **Given** 新草稿已提交；**Then** **必须重新审批**，**不继承**旧结论、不继承旧审批人意见作为"已同意"。层级 = 原层级（不降级）；若修改后动作类型升级（如 A-04→A-05），层级随之升为 L2 |
| 6 | 超限终止 | **Given** `exhausted` 且审批人驳回；**Then** 任务 → `failed`（**不进 `partial_success`**），两份草稿与结论**保留可查**，产生 `approval.rejected`，断言**无**草稿被标记为 approved |
| 7 | 审计事件 | 完整周期须按时间序存在：`approval.requested` → `approval.revision_requested` → `draft.superseded` → `draft.created(v2)` → `approval.requested(v2)` → `approval.approved`/`approval.rejected`；每事件含 `task_id`/`correlation_id`/`operator_id`/`timestamp` |
| 8 | 幂等 | **Given** 同一 `approval_request_id` 的重复"要求修改"（双击/重试）；**Then** 按 `correlation_id` 去重，`revision_count` **不重复递增**，返回与首次相同结果，**不重复写审计**。批准/驳回重复提交同样幂等 |
| 9 | 超时与不可用 | **超时**（**D-13 修订，按 D-11 统一**）：超过审批 TTL（**24h 常量，D-11 已确认，起算于审批请求创建时刻**）→ **`status=failed`（超时进失败态）** 且 `approval_expired=true`，`approval_phase` **退出等待**（依据 P0-003 §7.1：该字段仅在 `status=waiting_for_approval` 时有效），产生 `approval.expired`；**不自动批准、不自动驳回、不自动升级**（三者均为伪造一个不存在的人工决定），亦**不允许无限期保持等待**。此后收到结果须**重新发起审批**（新请求、新 TTL），旧请求作废、迟到结果不直接生效 —— 〔此句属 D-11 第 4 条的**推导规则，尚待负责人确认**，P1-004 §4 已明确未批准〕。<br>**Service 不可用**：修订稿生成失败 → 原草稿保持 `superseded`，**不生成**空稿/占位稿，任务 `failed`（若他 Agent 已成功可 `partial_success`），`revision_count` **不回滚**（防利用故障反复修改） |

> **第 9 点的 D-13 修订留痕（原文保留，不删除）**
>
> **V2.2 原文**：`超过审批 TTL（建议 24h，待确认）→ approval_expired=true，任务保持等待、不自动通过/拒绝/升级，approval.expired；此后收到结果须重新发起审批。`
>
> **冲突点**：「**任务保持等待**」与 D-11「**超时进失败态（`status=failed`）**」直接矛盾；且「建议 24h，待确认」与 D-11 已确认的 24h 常量不符。若按原文验收，会把已批准的 D-11 判为不合格（P1-003 报告 N-01）。
>
> **修订依据**：P1-004 / D-13 明确授权按 D-11 统一修订本点与 SC-077，并要求「不允许超时后无限期保持等待」。**修订未创造新状态名**——`failed` 是 P0-003 §7 九态之一。

**D-13 五项必查（逐项对照，V2.3）**

| # | 必须保证的行为 | 本文落点 | 是否可观察 |
|---|---|---|---|
| 1 | **不会自动批准** | §6.4 第 9 点「不自动批准」；SC-077「无任何审批结论」 | ✅ 断言 `status=failed` **且**无 `approval.approved` 事件 |
| 2 | **不会无限期等待** | §6.4 第 9 点「不允许无限期保持等待」；超时即 `failed` | ✅ `status` 不可能停在 `waiting_for_approval` |
| 3 | **进入既有失败状态** | `status=failed`（P0-003 §7 九态之一，**未新增状态**） | ✅ 状态值与既有枚举一致 |
| 4 | **审计记录能反映超时结果** | §6.4 第 9 点与 SC-077 均要求产生 **`approval.expired`** | ✅ 审计事件流中须存在该事件，且含 `task_id`/`correlation_id`/`timestamp` |
| 5 | **迟到结果如何处理** | §6.4 第 9 点：「须重新发起审批…迟到结果不直接生效」**并已标注为推导规则、尚待确认** | ⚠️ **规则本身未批准**（P1-004 §4），只能作为**待确认的配套行为**记录，不得当验收线 |

> **第 5 项的写法是刻意的**：P1-004 §4 明确"'须重新发起、迟到结果不生效'等推导规则"**未获批准**。因此本文**保留原句但加标注**，既不清空（会丢失既有设计意图），也不升级（会伪造决策）。
>
> **不得把它写成"已确认"** —— 这是 D-13 与 P1-004 §4 的交界处，**跨过去就是把推导当决策**。

**关联关系自检（修改次数 / 审批请求 / 草稿版本 / 审计事件）**

| 实体 | 关联键 | 约束 |
|---|---|---|
| `ApprovalRequest` | `approval_request_id` + `draft_id` + `round` | 每轮一条，`round ∈ {1,2}` |
| `Draft` | `draft_id` + `parent_draft_id` | v2 的 parent 必为 v1；v1 必为 `superseded` |

### 7.3 审批场景的期望值调整（D-07 影响，场景数不变）

6 个审批场景**数量不变**，但断言对象从"任务状态"改为"`(status, approval_phase)` 二元组"：

| 场景 | V2.0 断言（旧） | V2.1 断言（D-07 后） |
|---|---|---|
| L1 批准 | `status=completed` | `status=completed` + 产生批准记录、无业务执行 |
| L1 驳回 | `status=failed` | `status=failed` |
| 要求修改→重审→批准 | `status=waiting_for_approval` | `status=waiting_for_approval` **且** `approval_phase=waiting_revision` → 新稿后回到 `waiting_decision` → 批准 |
