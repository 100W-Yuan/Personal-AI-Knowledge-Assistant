## 2. 三条技术路线对比

### 路线 A：本地 Embedding（推荐方向）

| 维度 | 评估 |
|---|---|
| 候选模型 | ①**bge-small-zh-v1.5**（BAAI，512 维，约 95MB，中文优化，社区公认轻量基线）；②bge-m3（多语言，约 2.2GB FP32/1.2GB 量化，强但重）；③**nomic-embed-text via Ollama**（约 274MB，多语言一般，**无需新增任何 Python 依赖**——项目已有 `openai` 包可直接调 Ollama 的 OpenAI 兼容 `/v1/embeddings`） |
| 语言支持 | 本项目记忆全中文，bge-small-zh 或 bge-m3 最贴合；nomic 中文一般（**待实测确认**） |
| 体积/内存/速度 | bge-small-zh：内存约 0.5–1GB、CPU 单条 10–50ms 量级（**待实测**）；经 RTX 3050 或 Ollama 可再加速 |
| Windows/Python 兼容 | 三条子路线均兼容 Win11 + Py3.12；sentence-transformers 路线会引入 torch（约 2GB+ 依赖树）；**Ollama 路线零 Python 依赖、与现有架构最契合** |
| 新增依赖 | sentence-transformers 路线：+torch/transformers（重）；Ollama 路线：**0 个新 Python 包**（仅需下载嵌入模型文件） |
| 隐私/离线/维护 | 全部离线，记忆文本不出本机；维护点是 Ollama 服务可用性与模型版本固定 |
| 风险 | Ollama 服务未启动时需降级（见第 7 节）；模型输出维度/版本需在向量表中登记 |

### 路线 B：远程 Embedding API

| 维度 | 评估 |
|---|---|
| 候选 | OpenAI `text-embedding-3-small`（1536 维）；阿里云 DashScope `text-embedding-v3`；智谱 `embedding-3` 等 |
| 兼容性 | 项目已用 OpenAI 客户端（`agent.py:69`，base_url=api.deepseek.com）；**DeepSeek 是否提供 embedding 端点：待确认（本轮无网络调用，不做断言）** |
| 成本参数 | 计费按 token；估算需三要素：记忆库总 token、每轮查询 token、日查询量——当前库仅 5 条记忆（约几百 token），**成本量级可忽略**，但引入外部依赖 |
| 网络/隐私 | 每条用户记忆与查询都要出网；故障时需降级；API Key 管理沿用现有模式 |
| 结论 | 作为**备选**：适合无本地算力场景，但本项目已有 Ollama+独显，隐私与离线收益不明显 |

### 路线 C：混合检索（路线 A 的组合方式，见第 5 节架构）

- 精确 key 命中**保留最高优先级**（不动现有 `find_memory` 路径）
- 语义检索仅作为**第 2.5 层补充**：仅当"意图规则命中 + 关键词/补齐层未达到上限 3 条"时启用
- 两路分数**不做数值混合**（尺度不同：字符分 2–40 vs 余弦 0–1），改用**分层优先级**：精确 key > 关键词命中 ≥ 阈值 > 语义命中 ≥ 阈值，层内按各自原生分数排序，跨层按层序
- 类别过滤、id 去重、上限 3 全部复用现有逻辑

## 4. 离线评估矩阵设计（先设计、后实施；未运行不得伪造数据）

基于现有 A/B/C 系列测试扩展（沿用 `build_eval_agent` 临时库 + 固定虚构语料模式）：

| # | 用例 | 目标记忆 | 允许返回 | 禁止返回 | 考察点 |
|---|---|---|---|---|---|
| S1 | "我是什么专业的？" | major=计算机科学与技术 | — | 其他分类 | 语义召回核心场景（当前底层必漏） |

| S4 | 同主题 vs 无关："我平时喜欢做什么" vs "量子纠缠是什么" | preference / 无 | — | 全部 / 全部 | 相关性判别 |
| S5 | 多候选排序：3 条同类记忆 | 最新一条 | 其余同类 | 跨类 | 语义分排序（MRR） |
| S6 | 精确 key："我叫什么名字" | name | — | 其他 | 原路回归，不得退化 |
| S7 | 无关查询误召回：数学/天气/闲聊 6 例 | 无 | — | 全部 | 语义层零误召回 |
| S8 | 边界：空库、单条、重复 key、category 过滤 | 按场景 | 按场景 | 按场景 | 结构一致性 |

**验收指标（口径）**：
- Recall@3 = Σ|目标∩前3| / Σ|目标|（分子/分母逐例列出，同现有报告格式）
- Precision@3 = Σ|前3∩relevant| / Σ|前3|（relevant=目标∪允许）
- MRR = 各查询(1/首个相关名次)的均值
- 查询延迟：单次 `search` 端到端毫秒（p50/p95，测量 ≥20 次取分位）
- 成本：本地路线≈0 边际成本；API 路线按 token 单价×实测 token 计，**未运行前不给具体数字**

## 5. 推荐的最小侵入式架构（保留 SQLite，不引入向量数据库服务）

```
memory.py
  ├─ 现有 search_long_term_memory()          ← 完全不动（关闭开关时的唯一路径）
  ├─ 新增 _semantic_search()（同文件或新模块） ← 仅在被启用时调用
  │     └─ 经 Ollama 本地 /v1/embeddings（复用已装 openai 包）
  └─ retrieve_long_term_memories (agent.py:357)
        现有四层路径不变；仅当结果 < 上限 3 时，追加"语义层"补齐
```

1. **需修改模块**：`memory.py`（新增语义检索函数与开关读取）；`agent.py`（仅"补齐"分支加一个可关闭的调用，改动约 5–10 行）——两者都要求默认行为与现在完全一致
2. **新增模块**：建议独立 `semantic.py`（词元/向量逻辑不污染 memory.py 主流程），含：embed 调用、余弦相似度、向量表读写
3. **向量存储**：正式库新增表 `memory_vectors(id, memory_id, model, dim, vector BLOB, updated_at)`；BLOB 存 float32 数组字节。**是否必须改库结构：是**——但纯增量建表，不动现有表（见第 6 节）
4. **补建向量**：一次性回填脚本，先对**临时库副本**执行，人工核对后再经批准对正式库执行（当前仅 5 条，秒级）
5. **一致性**：`save_memory` 的 add/update 后触发向量重算；无删除接口，故暂无需级联删除；一致性以 `memory_id + model` 唯一约束保证
6. **开关**：环境变量 `MYAI_SEMANTIC_RETRIEVAL=off|on`（默认 **off**）；关闭时零新增代码路径被执行
7. **降级**：embed 调用 try/except + 2s 超时，任何异常（服务未启动/超时/维度异常）→ 直接跳过语义层，返回原有结果，绝不伪造
8. **测试隔离**：沿用 tmp_path 临时库模式；语义测试用**假 embed 服务**（本地函数替换）或对临时库真实调用本地 Ollama，两个层次分开：纯逻辑用假服务，效果用真实本地模型（离线、零 API 成本）
